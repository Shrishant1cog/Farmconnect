# FarmConnect — PostgreSQL Migration Guide

**Repository:** https://github.com/Shrishant1cog/Farmconnect
**Branch:** `fix/local-updates`
**Database:** PostgreSQL 15+ (verified on PostgreSQL 16 and 17)
**ORM:** Prisma 6.19.3

---

## 1. Why the database was migrated

The backend originally used SQLite:

```prisma
datasource db {
  provider = "sqlite"
  url      = "file:./dev.db"
}
```

SQLite cannot run on Render's managed PostgreSQL, cannot be shared safely between
the website and the Android app, and silently downgraded several PostgreSQL
features (case-insensitive `contains`, native enums, concurrent writes).

The backend is the single source of truth for **both** clients, so it now targets
PostgreSQL exclusively and the connection is fully environment driven.

---

## 2. What changed

### 2.1 Datasource

`backend/prisma/schema.prisma`:

```prisma
// The database connection is environment driven so the exact same schema can be
// used against the local docker PostgreSQL instance and the managed PostgreSQL
// database used in production (Render).
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

`DATABASE_URL` is **required**. `backend/src/config/env.ts` validates it with Zod
and fails fast when it is missing:

```ts
DATABASE_URL: z
  .string()
  .min(1, 'DATABASE_URL is required for database connectivity')
  .default(
    rawEnv.DATABASE_URL ||
      'postgresql://postgres:postgres@localhost:5432/farmconnect?schema=public'
  ),
```

### 2.2 Models and relations

**No model was deleted, renamed or simplified.** All 16 models keep their original
names, fields and business relationships:

| Model | Key relations |
| --- | --- |
| `User` | 1–1 `FarmerProfile`, 1–1 `ConsumerProfile`; 1–N `Order`, `Enquiry`, `Message`, `ChatMessage`, `Notification`, `Complaint` |
| `FarmerProfile` | 1–N `Product`, `Order`, `Enquiry`, `FavouriteFarmer` |
| `ConsumerProfile` | 1–N `FavouriteProduct`, `FavouriteFarmer` |
| `Category` | 1–N `Product` |
| `Product` | N–1 `FarmerProfile`, `Category`; 1–N `OrderItem`, `Enquiry`, `FavouriteProduct`, `PriceHistory`, `ChatMessage` |
| `PriceHistory` | N–1 `Product` |
| `Enquiry` | 1–N `Message` |
| `Message` | N–1 `Enquiry`, `User` |
| `ChatMessage` | N–1 `User` (sent / received), `Product` |
| `Order` | 1–N `OrderItem`; N–1 `User`, `FarmerProfile` |
| `OrderItem` | N–1 `Order`, `Product` |
| `ApmcMarketRate` | — |
| `FavouriteProduct` | N–1 `ConsumerProfile`, `Product` (`@@unique([consumerId, productId])`) |
| `FavouriteFarmer` | N–1 `ConsumerProfile`, `FarmerProfile` (`@@unique([consumerId, farmerId])`) |
| `Complaint` | N–1 `User` |
| `Notification` | N–1 `User` |

Enums are unchanged and are now implemented as **native PostgreSQL enum types**
(`Role`, `ContainerType`, `OrderStatus`, `EnquiryStatus`, `ComplaintStatus`).

### 2.3 Type mapping

| Prisma type | PostgreSQL type |
| --- | --- |
| `String` | `TEXT` |
| `Float` | `DOUBLE PRECISION` |
| `Int` | `INTEGER` |
| `Boolean` | `BOOLEAN` |
| `DateTime` | `TIMESTAMP(3)` |
| `String @id @default(uuid())` | `TEXT` primary key, UUID generated by Prisma |
| enum | native `CREATE TYPE ... AS ENUM (...)` |

### 2.4 Query compatibility fixes

| Issue | Location | Fix |
| --- | --- | --- |
| `consumerProfile.address` does not exist in the schema — the field is `deliveryAddress`. Registration and profile updates silently wrote nothing (the `try/catch` swallowed the Prisma error). | `backend/src/modules/auth/auth.controller.ts`, `backend/src/modules/users/users.controller.ts` | Both now write `deliveryAddress`. The swallowing `catch` was removed so failures surface. |
| Product search used a case-sensitive `contains`, which was a SQLite workaround. | `backend/src/modules/products/products.controller.ts` | Restored PostgreSQL's native `mode: 'insensitive'` for `search` and `district`. |
| The public farmer directory filtered with `contains` without `mode`. | `backend/src/modules/users/users.controller.ts` | Added `mode: 'insensitive'`. |
| `add-categories.ts` upserted by `slug` only, but `Category.name` is also unique. The seed uses short slugs (`grains` for `Grains & Millets`) while the script generated `grains-millets`, producing `P2002`. | `backend/add-categories.ts` | The script now resolves the category by name **or** slug before updating. |

## 3. Migration files

| Path | Purpose |
| --- | --- |
| `backend/prisma/migrations/20260101000000_init/migration.sql` | Full PostgreSQL schema: 16 tables, 43 indexes, 5 enums, all foreign keys |
| `backend/prisma/migrations/migration_lock.toml` | Pins the migration history to the `postgresql` provider |

The migration was generated from the Prisma schema with:

```bash
cd backend
npx prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/20260101000000_init/migration.sql
```

> **Windows note:** redirecting the output with `>` / `Out-File -Encoding utf8` writes a
> **UTF-8 BOM**, which PostgreSQL rejects with
> `ERROR: syntax error at or near "﻿"`. The committed file is BOM-free
> (first bytes are `2D 2D 20`, i.e. `-- `). When regenerating the migration on
> Windows, strip the BOM, for example:
>
> ```powershell
> npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script |
>   Out-File -Encoding utf8 migration_raw.sql
> $raw   = Get-Content migration_raw.sql -Raw
> $clean = $raw.TrimStart([char]0xFEFF)
> [System.IO.File]::WriteAllText(
>   'prisma\migrations\20260101000000_init\migration.sql',
>   $clean,
>   (New-Object System.Text.UTF8Encoding($false))
> )
> ```

## 4. Running the database locally

### 4.1 Option A — Docker (recommended)

`docker-compose.yml` at the repository root:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: farmconnect-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: farmconnect
      POSTGRES_PASSWORD: farmconnect
      POSTGRES_DB: farmconnect
    ports:
      - "5432:5432"
    volumes:
      - farmconnect-postgres:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U farmconnect -d farmconnect"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  farmconnect-postgres:
```

```bash
docker compose up -d postgres
```

> **Windows caveat:** Docker Desktop on Windows requires WSL 2 or Hyper-V. If
> `docker info` fails with `500 Internal Server Error`, either enable WSL 2
> (`wsl --install`, requires a reboot) or run a native PostgreSQL installation.
> A portable PostgreSQL distribution (for example the
> `embedded-postgres` npm package) works just as well for local verification.

### 4.2 Option B — native PostgreSQL

Install PostgreSQL 15 or newer and create the database:

```sql
CREATE USER farmconnect WITH PASSWORD 'farmconnect';
CREATE DATABASE farmconnect OWNER farmconnect;
```

### 4.3 Configure the connection string

Copy the example file and edit it:

```bash
cp backend/.env.example backend/.env
```

```dotenv
DATABASE_URL="postgresql://farmconnect:farmconnect@localhost:5432/farmconnect?schema=public"
```

### 4.4 Apply the schema and seed

```bash
cd backend
npm install
npm run db:setup
```

`db:setup` chains the three commands below:

| Command | What it does |
| --- | --- |
| `npm run db:migrate` | `prisma migrate deploy` — applies `20260101000000_init` |
| `npm run db:seed` | `prisma/seed.ts` — demo farmers, consumers, admin, categories, listings, enquiries and orders |
| `npm run db:categories` | `add-categories.ts` — syncs the full agricultural category list |

Individual commands:

```bash
npx prisma generate            # regenerate the Prisma client
npx prisma migrate deploy      # apply migrations (production-safe)
npx prisma migrate dev         # create a new migration (development only)
npx prisma migrate status      # verify the schema is up to date
npx prisma studio              # browse the data in a GUI
```

## 5. Migrating an existing SQLite database to PostgreSQL

If you already have data in `backend/prisma/dev.db`, export it before switching.

### 5.1 Export from SQLite

```bash
cd backend
sqlite3 prisma/dev.db .dump > legacy_dump.sql
```

### 5.2 Create the PostgreSQL schema

```bash
npm run db:migrate
```

### 5.3 Re-seed and reconcile

The seed script wipes and recreates the demo data set. For production data,
either

* replay `legacy_dump.sql` into PostgreSQL with `psql -f legacy_dump.sql`
  (review the `INSERT` statements first — SQLite booleans are `0/1` while
  PostgreSQL expects `false/true`, and SQLite dates are text), or
* write a one-off migration script that copies row by row through the Prisma
  client, which handles the type conversion automatically.

> The seed script deletes all existing rows before inserting the demo data.
> **Never run `npm run db:seed` against a production database.**

## 6. Production migration (Render managed PostgreSQL)

> The project owner performs the Render deployment. This section documents the
> exact steps; the agent does not run them.

1. Create the PostgreSQL instance in Render and copy the **Internal Database URL**.
   It looks like:
   `postgresql://farmconnect_user:<password>@<host>:5432/farmconnect`
2. Add it to the backend web service as the `DATABASE_URL` environment variable.
3. On the **first deploy**, set the build command to:

   ```bash
   npm ci && npm run db:generate && npm run build && npm run db:migrate
   ```

   and the start command to:

   ```bash
   npm start
   ```

   `prisma migrate deploy` only applies pending migrations and never drops data,
   so it is safe to leave in the build command for every deploy.
4. If the owner prefers to run migrations manually, use a one-off Render shell:

   ```bash
   cd backend && npx prisma migrate deploy
   ```

5. Verify the database is reachable through the health probe:

   ```bash
   curl https://<your-api-host>/api/health
   ```

   Expected response when the database is up:

   ```json
   {
     "status": "UP",
     "service": "FarmConnect Engine",
     "database": "UP",
     "uptime": 42,
     "timestamp": "2026-01-01T00:00:00.000Z"
   }
   ```

   The endpoint returns **HTTP 503** with `"database": "DOWN"` when the database
   cannot be reached, which lets Render mark the service as unhealthy.

### 6.1 Important: `DIRECT_URL` vs. `DATABASE_URL`

For managed PostgreSQL providers that use a connection pooler (PgBouncer),
Prisma needs the direct (non-pooled) connection for migrations:

```dotenv
DATABASE_URL="postgresql://...:5432/farmconnect?pgbouncer=true&connection_limit=1"
DIRECT_URL="postgresql://...:5432/farmconnect"
```

Add `directUrl = env("DIRECT_URL")` to the datasource when the provider requires
it.

## 7. Health checks and observability

`GET /api/health` performs a real `SELECT 1` probe against PostgreSQL and
returns `503` when it fails, so it is safe to use as the Render health check
path.

Other operational notes:

* The Prisma client is cached on `globalThis` outside production so hot reloads
  do not exhaust the connection pool.
* `backend/src/config/db.ts` logs only errors in production.
* `prisma migrate status` should report *"Database schema is up to date!"*.

## 9. Rollback

`prisma migrate deploy` never removes data. To roll back to the pre-migration
state, take a snapshot of the database first (Render: *Backups → Create backup*),
then restore it. The initial migration is the only one, so rolling the schema
back means dropping the PostgreSQL database and recreating it with
`npm run db:migrate && npm run db:seed`.
